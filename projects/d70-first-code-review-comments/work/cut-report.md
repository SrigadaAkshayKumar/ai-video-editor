## Clean script (what the viewer will hear)

Your first code review comment will arrive within weeks of joining, and the way you reply to it can decide how your team sees you for the next year. This video is for every fresher who is about to push code at work for the first time. By the end, you will know three rules for handling review comments, and the one reply that makes seniors stop trusting you. Stay till the end because rule number three is the one almost everyone gets wrong. First, what is a code review before your code goes into the main project, a teammate reads it and leaves comments. Usually, this happens on a pull request in tools like GitHub, GitLab, or Bitbucket. Picture this Ravi, a fresher, sends his first pull request. By evening, he sees 11 comments, his stomach drops. He thinks, "I have failed." But he has not. Review is how every team, even the best ones, keeps its code healthy. Google's Public Engineering Guide says it clearly. A comment is the reviewer trying to help you and the code, not an attack on you. So, take a breath. 11 comments on a first pull request is normal. Rule number one, fix the code, do not just explain it. Say a reviewer writes, "I do not understand this part." Many fresher reply with a long explanation in the comment box. That helps one person once. A better move is to change the code itself. Rename the variable, split the long function, or add a short comment above the line saying why it is there. Google's Guide gives the same advice. If a reviewer did not understand your code, future readers will not either. So, your first response to confusion is to make the code clearer and only then reply. Rule number two, if you do not understand the comment, ask if you disagree, discuss. Never argue. Suppose a reviewer says, "Use a different approach here." Do not write, "No, I will not change it." That sounds defensive and it stays in the tool forever. Write something like this, "I chose this approach because it was simpler to test." Do you think the other approach handles our case better? Or should we weigh the trade-off differently? See the difference? You gave your reason and you asked a question. Sometimes you know something about the task that the reviewer does not. This way, you share it politely and you both reach the right answer. And if a comment makes you angry, close the laptop, take a short walk, and reply when you are calm now. Rule number three, the one most freshest miss, keep your pull requests small. Why does this matter for comments? Because a huge pull request gets huge, painful feedback and reviewers are slower to read it. Google's guide says a hundred lines is usually a reasonable size and a thousand lines is usually too large. It also says reviewers can reject a change just for being too big. So, send one change that does one thing. Include its test. If your task is big, split it into small steps and send them one by one. A fresher who sends small pull requests gets faster replies, fewer comments and a name for being easy to review. That is how you build trust without saying a word. So, what do you do this week before you send your pull requests? Read it yourself first line by line as if you were the reviewer. You will catch many comments before anyone writes them. When comments arrive, reply to everyone. Write them when you fix it. Write a question when you do not understand. Never leave a comment hanging with no answer. And what was the reply that caused trust, silence or a defensive no? Fix the code, ask, do not argue, keep it small. Those are the three rules.
